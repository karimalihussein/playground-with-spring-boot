Educational map: REST vs gRPC in this repo

Open the code next to this page. The benchmark module lives in com.playground.bench and uses one shared service: NumberBenchService → NumberGenerationCore.squares(count).

REST path (HTTP + JSON)

  1. Browser or ab opens TCP to localhost:8080.
  2. Tomcat handles HTTP (often HTTP/1.1 in local setups; HTTP/2 for plain Spring MVC is a separate configuration story).
  3. Spring MVC routes GET /rest/unary/{count} to UnaryNumbersRestController.
  4. Jackson (tools.jackson.databind.ObjectMapper in Spring Boot 4) turns NumbersJsonResponse into UTF-8 JSON bytes.
  5. The response body travels as text—human-readable, cache-friendly in some CDNs, but heavier for big numeric arrays than Protobuf.

Read: ApacheBench docs · HTTP Semantics (RFC 9110)

gRPC path (HTTP/2 + Protobuf)

  1. GrpcBenchClient opens a ManagedChannel to localhost:9090 (plaintext for education).
  2. gRPC sits on HTTP/2, so many calls can multiplex over one connection using separate streams; see RFC 9113.
  3. Your unary method builds a GenerateNumbersResponse Protobuf message (NumberBenchGrpcService).
  4. The library emits binary frames (length-prefixed gRPC messages), not a JSON string. Field tags + compact integer encodings dominate on the wire; see Protobuf Encoding.

Read: gRPC Core Concepts

Streaming (visual mental model)

  • REST unary: request → response → done (connection may be reused).
  • REST SSE (/rest/stream/{n} and alias /grpc/stream/{n} on port 8080): one HTTP response stays open; server pushes many data: lines — still HTTP, not the gRPC protocol.
  • gRPC unary: one request message + one response message on one HTTP/2 stream for that RPC.
  • gRPC streaming: one HTTP/2 stream carries many Protobuf messages until half-close/complete — compare server-stream, client-stream, and bidi in NumberBenchGrpcService.

Read: gRPC over HTTP/2 · WebSockets (RFC 6455) (browser-native duplex, different framing)

Why people see higher gRPC throughput (not a law of physics)

  • Smaller payloads for structured numeric data (JSON text is verbose).
  • HTTP/2 multiplexing reduces connection churn and lifts concurrency.
  • Head-of-line blocking at TCP still exists, but HTTP/2 avoids application-level HOL blocking that naive HTTP/1.1 pipelining hit.
  • Your JVM still does work: serialization + business logic dominate for tiny payloads; measure before declaring a winner.
